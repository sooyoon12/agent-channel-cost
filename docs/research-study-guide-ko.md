# 구조화 도구 관측 전처리 연구: 이해·발표·첨삭 가이드

이 문서는 현재 논문 `paper/main.tex`의 연구를 처음부터 끝까지 이해하고, 발표를 준비하고,
문장을 직접 첨삭할 수 있도록 정리한 학습용 해설서다. 논문의 축약본이 아니라 다음 질문에
답하기 위한 문서다.

- 처음 초안은 무엇을 했고 왜 약했는가?
- 어떤 실험을 추가했으며 그 추가가 논문의 주장을 어떻게 바꾸었는가?
- 현재 논문의 각 숫자는 어디서 나왔고 무엇을 의미하는가?
- 이 연구가 주장하는 것과 주장하지 않는 것은 무엇인가?
- 교수님이나 심사위원이 물을 만한 질문에는 어떻게 답해야 하는가?
- 원고를 수정할 때 무엇을 지키고 무엇을 줄여야 하는가?

---

## 1. 연구를 한 문장으로 설명하면

> 도구 사용 에이전트의 구조화된 조회 결과를 줄일 때는 단순히 많이 자르는 것보다,
> 다음 행동에 필요한 레코드와 필드를 남기는 것이 성공당 비용을 결정한다.

조금 더 정확히 말하면, 이 연구는 구조화된 도구 관측을 짧게 만드는 세 가지 규칙을
비교하고, 실행당 비용뿐 아니라 실패 비용까지 포함한 **성공당 비용**으로 평가한다.

1. 균등 절단: 목록 전체에서 등간격 위치의 레코드를 남긴다.
2. Head-tail 절단: 목록의 앞과 뒤에 있는 레코드를 남긴다.
3. 관련도 선별: 사용자 요청에 나타난 값과 많이 일치하는 레코드를 먼저 남긴다.

결과적으로 위치만 보는 두 방법은 관측을 줄여도 성공 손실 때문에 성공당 비용을 안정적으로
낮추지 못했다. 반면 무엇이 요청과 관련 있는지를 보는 단순한 선별은 성공률이 일부 낮아지는
조건에서도 성공당 비용을 16.7--57.3% 낮췄다.

## 2. 연구 대상은 정확히 무엇인가

### 2.1 에이전트가 하는 일

이 연구의 에이전트는 다음 순서로 작동한다.

1. 사용자의 요청을 읽는다.
2. 검색 API를 호출한다.
3. API가 반환한 구조화 JSON 목록을 읽는다.
4. 목록에서 조건을 만족하는 레코드나 이벤트를 찾는다.
5. 해당 ID와 필요한 인자를 사용해 제출 또는 상태 변경 API를 호출한다.

여기서 **도구(tool)**는 검색 엔진 일반을 뜻하지 않는다. 레코드 또는 일정을 조회하고,
그 결과를 바탕으로 상태를 갱신하는 결정적 외부 API를 뜻한다. 검색 API는 실험 도구 중
하나이며, 웹 검색 엔진을 평가하는 연구는 아니다.

### 2.2 개입 지점

전처리는 검색 API가 JSON을 반환한 뒤, 그 JSON이 다음 모델 호출에 들어가기 전에 수행된다.

```text
사용자 요청 → 모델의 검색 호출 → 검색 API의 JSON 결과
                               ↓
                         관측 전처리
                               ↓
                 짧아진 JSON → 모델의 후속 행동
```

따라서 AI끼리 직접 공유하는 내부 표현에 연구자가 끼어드는 것이 아니다. 애플리케이션
개발자가 통제하는 모델--도구 middleware에서, API 반환값을 다음 모델 요청에 넣기 전에
결정적 함수를 적용한다. 일반적인 API 기반 agent loop에서 구현 가능한 개입이다.

### 2.3 왜 현재 원고는 ‘압축’보다 ‘전처리·절단·선별’을 쓰는가

교수님이 지적한 것처럼 ‘압축’은 압축 해제와 원본 복원을 연상시킬 수 있다. 하지만 이
연구의 방법은 일부 레코드를 버리는 손실 변환이며 복원을 전제하지 않는다.

- 전체 개념: **도구 관측 전처리** 또는 **손실 축약**
- 위치를 기준으로 버리는 방법: **절단**
- 요청 관련도를 기준으로 고르는 방법: **선별**
- 하지 않는 것: 새로운 문장을 생성하는 요약, 무손실 압축, 압축 해제

관련도 선별도 생성형 요약이 아니다. 기존 JSON 레코드 중 일부를 그대로 남기는 추출형
전처리다. 따라서 ‘요약’이라고만 부르면 생성형 요약과 혼동될 수 있다.

## 3. 과제와 데이터 구성

### 3.1 두 과제 유형

#### Long 과제: 의미쌍 60개

긴 레코드 목록에서 지역, 상태, 범주, 우선순위, 금액, 위험 점수, 날짜 등의 조건을 모두
만족하는 레코드를 찾는다. 이후 레코드 ID와 evidence code를 제출한다.

#### Event 과제: 의미쌍 15개

일정 검색 결과에서 장소 조건을 만족하는 이벤트를 찾고, 해당 event ID로 출석 상태를
갱신한다.

합계는 75개 의미 구조다. 각 의미 구조에 한국어 요청과 영어 요청을 하나씩 만들었으므로
조건당 실행은 150회다.

### 3.2 의미쌍이라는 말의 의미

한국어 요청과 영어 요청은 표현만 다르고 같은 hidden state와 같은 정답을 공유한다. 따라서
통계적으로 완전히 독립된 150개 과제로 취급하면 표본 수를 부풀리게 된다. 이 연구는
불확실성을 계산할 때 `pair_id`, 즉 75개 의미쌍을 재표집 단위로 사용한다.

### 3.3 개발 세트와 보류 세트

- 개발: long 20쌍 + event 5쌍 = 25쌍
- 보류 평가: long 60쌍 + event 15쌍 = 75쌍

개발 과정의 네 차례 조정에서 B0 성공률은 100%, 86%, 조기 중단, 96%였다. 이후 보류
과제와 분석 기준을 체크섬으로 고정했다. 이 이력은 연구자가 난이도를 조정했다는 사실을
숨기지 않고, 개발과 최종 평가를 분리했다는 투명성 근거다.

## 4. 처음 실험은 무엇이었나

### 4.1 1차 실험의 구성

1차 실험은 다섯 조건을 각각 150회 실행해 총 750회였다.

- B0: 전처리하지 않은 기준선
- 균등 절단 0.8
- Head-tail 절단 0.8
- Schema-oracle
- Query-aware oracle

Schema-oracle은 미리 아는 schema 정보를 사용해 불필요하다고 선언된 필드를 제거한다.
Query-aware는 생성기의 완전한 구조화 조건을 받아 결과를 필터링한다. 둘 다 현실적인 일반
방법이 아니라, 잘 보존했을 때 얻을 수 있는 낙관적 참조점이다.

### 4.2 1차 실험에서 알게 된 것

| 조건 | 성공률 | 실행당 비용 변화 | 성공당 비용 변화 |
|---|---:|---:|---:|
| B0 | 97.3% | 기준 | 기준 |
| 균등 절단 0.8 | 81.3% | -16.0% | +0.6% |
| Head-tail 0.8 | 74.0% | +5.2% | +38.4% |
| Schema-oracle | 98.7% | -11.8% | -13.0% |
| Query-aware oracle | 100% (150/150) | -80.5% | 낙관적 참조 |

균등 절단은 실행 하나의 비용을 16.0% 줄였지만 성공률도 거의 같은 비율로 낮췄다.
비용 비는 0.840, 성공률 비는 0.836이었고 두 효과가 상쇄되어 성공당 비용 비가 1.006,
즉 +0.6%가 됐다.

이 장면은 “싸게 실패하는 것은 효율 개선이 아니다”라는 연구 동기를 잘 보여줬다. 하지만
초안에는 두 가지 큰 약점이 있었다.

1. 유지율이 0.8 한 점뿐이라 비용--성공 곡선이 없었다.
2. 위치 절단 두 개와 oracle만 있어, 현실적으로 쓸 수 있는 중간 방법이 없었다.

그래서 당시 논문은 “당연한 결과를 엄밀하게 측정했다” 또는 “측정 프로토콜만 제안한다”는
평가를 받을 위험이 있었다.

## 5. 무엇을 추가로 보강했나

### 5.1 유지율 sweep

위치 기반 방법에 0.6과 0.9를 추가했다.

- 균등 절단: 0.6, 0.8, 0.9
- Head-tail: 0.6, 0.8, 0.9

0.8은 1차 실험 값이며 0.6과 0.9는 후속 실험 값이다. 이렇게 해서 유지율에 따라 비용과
성공이 어떻게 변하는지 곡선으로 볼 수 있게 됐다.

### 5.2 현실적 비-oracle 기준선: 관련도 선별

사용자 요청에 그대로 나타난 scalar 값과 각 레코드 값의 일치 수로 관련도를 매긴다.
관련도가 낮은 레코드부터 제거한다.

예를 들어 요청에 `region=WEST`, `status=REVIEW`가 있으면 이 값을 포함한 레코드가 높은
점수를 받는다. 다음 정보는 사용하지 않는다.

- 정답 ID
- 생성기가 보유한 구조화 의미 표현
- 어떤 필드가 안전하게 제거 가능한지에 대한 oracle 선언
- 별도의 모델 호출

불투명 ID, code, notes, 긴 서술 필드는 점수에서 제외한다. 구현은 단순 substring 기반이며,
새로운 학습형 압축기를 제안하는 논문은 아니다.

관련도 선별은 목표 유지율 0.8, 0.4, 0.2에서 실행했다. 0.4와 0.2는 오프라인 잔존 감사를
본 뒤 선택했으므로 사후·탐색 조건이라고 공개해야 한다.

### 5.3 동시기 B0 재실행

1차 B0와 후속 실험 사이에는 실행 시점 차이가 있었다. 모델 또는 provider 변화가 결과에
섞였다는 지적을 막기 위해 B0 150회를 후속 조건과 interleave해 다시 실행했다.

- 1차 B0: 146/150 성공, 성공률 97.3%
- 동시기 B0: 146/150 성공, 성공률 97.3%
- 실행당 비용 차이: +0.568%, 원고에서는 +0.6%
- 개별 실행 결과가 서로 달랐던 인스턴스: 4/150, 2.7%

따라서 집계 수준의 drift는 매우 작았고, 1차 실험의 0.8 점을 후속 곡선에 함께 놓을 수
있었다. 동시에 같은 B0를 반복해도 일부 개별 결과는 달라진다는 확률 변동도 측정했다.

### 5.4 후속 실험의 실행 수

후속 계획은 총 1,200회다.

- 동시기 B0: 150회
- 균등 0.6, 0.9: 300회
- Head-tail 0.6, 0.9: 300회
- 관련도 선별 0.8, 0.4, 0.2: 450회

따라서 논문 전체 실행 수는 다음과 같다.

```text
1차 실험 750회 + 후속 실험 1,200회 = 총 1,950 trajectory
```

후속 실험은 누락, 중복, task checksum 불일치, 분석 무효 없이 1,200개 계획 실행이 모두
완료됐다. 재시도 시도 한 건 때문에 원시 로그 줄 수는 계획 실행 수보다 하나 많지만,
분석에서는 plan ordinal당 최종 연구 결과 하나만 사용한다.

## 6. 현재 최종 결과

후속 비교의 기준은 동시기 B0다. 0.8 위치 절단만 1차 실험의 B0와 비교한 기존 값이다.

| 방법 | 목표 유지율 | 실현 유지율 | 성공률 | 실행당 비용 변화 | 성공당 비용 변화 | 95% CI |
|---|---:|---:|---:|---:|---:|---:|
| 균등 절단 | 0.6 | 0.579 | 50.7% | -36.1% | +22.7% | [1.7, 56.5]% |
| 균등 절단 | 0.8 | 0.789 | 81.3% | -16.0% | +0.6% | [-10.7, 15.5]% |
| 균등 절단 | 0.9 | 0.888 | 89.3% | -9.3% | -1.2% | [-8.4, 8.2]% |
| Head-tail | 0.6 | 0.579 | 46.7% | -3.8% | +100.6% | [49.8, 180.2]% |
| Head-tail | 0.8 | 0.789 | 74.0% | +5.2% | +38.4% | [15.2, 69.6]% |
| Head-tail | 0.9 | 0.888 | 86.0% | +1.7% | +15.1% | [2.3, 31.2]% |
| 관련도 선별 | 0.2 | 0.188 | 74.7% | -67.2% | -57.3% | [-61.6, -51.6]% |
| 관련도 선별 | 0.4 | 0.397 | 86.7% | -50.1% | -43.9% | [-47.9, -38.8]% |
| 관련도 선별 | 0.8 | 0.791 | 98.7% | -15.6% | -16.7% | [-19.4, -13.9]% |

### 6.1 위치 기반 절단의 해석

균등 절단 0.6은 실행당 비용을 크게 낮췄지만 성공률이 50.7%까지 떨어져 성공당 비용이
오히려 22.7% 증가했다. 0.9에서는 성공당 비용 점추정이 -1.2%지만 신뢰구간이 0을
포함하므로 안정적인 절감이라고 말할 수 없다.

Head-tail은 세 운용점 모두 성공당 비용이 증가했다. 특히 0.6에서는 실행당 비용이 겨우
3.8% 줄었는데 성공률은 46.7%여서 성공당 비용이 100.6% 증가했다.

따라서 “더 많이 남기면 무조건 해결된다”도 아니고 “적게 남기면 비용이 절감된다”도 아니다.
정답 정보가 목록의 어느 위치에 있는지 고려하지 않으면 위치 절단은 불안정하다.

### 6.2 관련도 선별의 해석

관련도 선별 0.8은 B0보다 성공이 오히려 두 건 많았지만, 통계적으로 성공률 차이는 검출되지
않았다(Holm 보정 p=1.0). 성공률 98.7%를 유지하면서 실행당 비용을 15.6%, 성공당 비용을
16.7% 줄였다. 가장 실용적인 운용점으로 해석할 수 있다.

0.4와 0.2에서는 성공률이 각각 86.7%, 74.7%로 낮아진다. 그러나 실행당 비용 감소가
50.1%, 67.2%로 더 커서 실패 비용을 포함해도 성공당 비용은 43.9%, 57.3% 감소한다.
즉 성공률만 보면 열화지만, 비용과 성공을 함께 보면 효율적인 운용점이 될 수 있다.

### 6.3 논문의 새 헤드라인

보강 전 결론은 다음에 가까웠다.

> 관측을 줄였다는 사실만으로는 효율 개선을 주장할 수 없고 성공당 비용을 측정해야 한다.

보강 후에는 한 단계 더 나아간다.

> 위치만 보고 줄이면 성공 손실이 비용 절감을 상쇄하지만, 다음 행동과 관련된 정보를
> 선택하면 같은 또는 더 강한 축약에서도 성공당 비용을 낮출 수 있다.

즉 기여가 단순한 측정 절차에서 **실제 설계 원칙과 실증적 발견**으로 확장됐다.

## 7. 성공당 비용을 반드시 이해해야 하는 이유

방법 m의 성공당 비용은 다음과 같다.

```text
성공당 비용 = 모든 실행의 총비용 / 성공한 실행 수
```

수식으로는 다음과 같다.

```text
C_success(m) = Σ_i C_mi / Σ_i y_mi
```

실패한 실행의 비용도 분자에 포함한다. 실패 행을 제거하고 성공한 실행만 평균 내면, 자주
실패하는 방법이 싸게 보이는 오류가 생긴다.

기준선과의 비율은 다음처럼 분해된다.

```text
성공당 비용 비 = 실행당 비용 비 / 성공률 비
```

예를 들어 균등 절단 0.8에서는 다음과 같다.

```text
실행당 비용 비 = 0.840
성공률 비       = 0.836
성공당 비용 비 = 0.840 / 0.836 ≈ 1.006
```

실행당 비용은 16% 줄었지만 성공률도 비슷하게 줄어 실제 효율은 개선되지 않았다.

## 8. 오프라인 정답 필드 잔존 감사

### 8.1 무엇을 검사했나

결정적 전처리기를 원래 도구 관측에 다시 적용한 뒤 다음 필드가 남았는지 검사했다.

- Long: 정답 record ID, evidence code, 지역, 상태, 범주, 우선순위, 금액, 위험 점수, 날짜
- Event: 정답 event ID와 장소

이 과정에는 모델 API 호출이 필요 없다. 전처리기의 출력만 검사한다.

### 8.2 run 단위 결과

| 방법 | 목표 유지율 | 잔존 후 성공 | 잔존 후 실패 | 삭제 후 성공 | 삭제 후 실패 |
|---|---:|---:|---:|---:|---:|
| 균등 | 0.6 | 76 | 0 | 0 | 74 |
| 균등 | 0.9 | 134 | 0 | 0 | 16 |
| Head-tail | 0.6 | 70 | 2 | 0 | 78 |
| Head-tail | 0.9 | 129 | 7 | 0 | 14 |
| 관련도 선별 | 0.2 | 112 | 0 | 0 | 38 |
| 관련도 선별 | 0.4 | 130 | 1 | 0 | 19 |
| 관련도 선별 | 0.8 | 148 | 2 | 0 | 0 |
| **합계** |  | **799** | **12** | **0** | **239** |

삭제된 239개 실행은 전부 실패했고, 삭제 후 성공은 한 건도 없었다. 잔존 후 실패는 12건뿐
이었다. 이는 필요한 행동 정보가 남는 것이 성공의 필요조건에 가깝다는 증거다. 다만
Head-tail처럼 정보가 남았는데도 모델이 실패할 수 있으므로 충분조건은 아니다.

### 8.3 재현성 보강

`scripts/reproduce_v2_retention_table.py`는 다음을 수행한다.

1. 로그에서 plan ordinal별 최종 실행 결과를 복원한다.
2. 동일한 결정적 도구 환경에서 첫 조회 결과를 다시 만든다.
3. 같은 전처리기를 같은 tokenizer로 다시 실행한다.
4. 원본과 전처리 출력의 SHA-256 handle을 로그의 handle과 대조한다.
5. 정답 필드 잔존과 실제 성공을 run 단위로 교차 집계한다.

1,050개 전처리 실행이 모두 해시 매칭됐고 표의 7개 셀이 모두 재현됐다. 따라서 표 3은
셀 단위 숫자를 추측해서 만든 것이 아니라, 실제 각 실행과 결정적 출력을 연결해 만든 결과다.

## 9. 통계는 어떻게 읽어야 하나

### 9.1 Bootstrap 신뢰구간

성공당 비용 변화의 95% 신뢰구간은 75개 의미쌍을 10,000회 복원추출해서 계산했다.
한국어와 영어를 따로 뽑지 않고 같은 의미쌍으로 함께 뽑는다.

- CI 전체가 0보다 아래: 성공당 비용 감소가 데이터에서 안정적으로 관찰됨
- CI 전체가 0보다 위: 성공당 비용 증가가 안정적으로 관찰됨
- CI가 0을 포함: 감소 또는 증가 방향이 불확실함

예를 들어 관련도 선별 0.8의 CI는 [-19.4, -13.9]%이므로 절감 방향이 분명하다. 균등
절단 0.9의 CI는 [-8.4, 8.2]%라서 -1.2%라는 점추정만 보고 절감됐다고 말하면 안 된다.

### 9.2 Strict-pair McNemar와 Holm 보정

Strict-pair 성공은 한 의미쌍의 한국어와 영어 실행이 모두 성공했을 때만 성공으로 센다.
McNemar 검정은 B0와 방법 사이에서 성공 상태가 바뀐 의미쌍의 비대칭을 본다. 일곱 후속
비교를 동시에 보므로 Holm 보정을 적용했다.

하지만 후속 조건과 Holm 보정은 완전한 사전등록 연구가 아니다. 특히 관련도 선별 0.4와
0.2는 오프라인 잔존 결과를 본 뒤 선택했다. 따라서 p값은 탐색적으로 해석해야 하며, 논문의
주요 메시지는 효과 크기, 신뢰구간, 잔존 대응에 둔다.

## 10. 비용 회계는 무엇을 측정하나

로컬에서는 모델 입력을 다음처럼 분리했다.

- I: 지시와 대화 이력
- T: 도구 관측
- O: 모델 출력
- P: provider가 보고한 입력 token
- R = P - I - T: 로컬에서 배분되지 않은 protocol residual

총비용은 로컬 I/T 합으로 추정하지 않고 provider usage에 가격표를 적용해 계산한다. 따라서
residual이 존재해도 총비용 결론은 바뀌지 않는다. residual은 회계 투명성을 위해 보존한다.

현재 모델과 가격 조건은 `gpt-5.6-terra`, reasoning effort low, 비캐시 입력 100만 token당
2달러, 출력 12달러다. 논문 비교는 캐시 상태의 우연한 차이를 피하기 위해 비캐시 정가로
환산한 list-price를 사용한다.

## 11. 한국어와 영어 결과는 무엇을 말하나

이 연구는 언어 성능 비교를 목적으로 설계하지 않았다. 한국어와 영어는 같은 의미 구조의
종속 반복이다. 동시기 B0에서 한국어/영어 provider 입력 token 비는 평균 1.032, 중앙값
1.005였다. 즉 이 합성 과제에서는 언어별 provider 입력 비용 차이가 작았다.

따라서 “한국어가 영어보다 몇 배 비싸다” 또는 “한국어에서도 일반화됐다”고 주장하면 안
된다. 한국어 surface를 포함한 이유는 동일 의미 구조에 대한 표현 변화와 의미쌍 군집 분석을
가능하게 하기 위해서다.

## 12. 연구가 주장하는 것과 주장하지 않는 것

### 주장할 수 있는 것

1. 구조화된 조회 결과에서 위치 기반 절단은 유지율 0.6--0.9 범위에서 성공당 비용을
   안정적으로 낮추지 못했다.
2. 요청의 표면값과 레코드의 일치를 이용한 관련도 선별은 이 합성 과제에서 성공당 비용을
   16.7--57.3% 낮췄다.
3. 정답 행동 필드의 오프라인 잔존은 실제 실패를 매우 잘 설명했다.
4. 실행당 비용만이 아니라 실패 비용을 포함한 성공당 비용을 함께 봐야 한다.
5. 배포 전에는 목표 축약률보다 보호할 행동 필드와 레코드 선택 규칙을 먼저 정해야 한다.

### 주장하면 안 되는 것

1. 관련도 선별이 모든 실제 에이전트 로그에서 같은 절감률을 낸다.
2. 새로운 최첨단 학습형 압축기를 제안했다.
3. 유지율 0.2가 모든 환경의 최적점이다.
4. 정답 필드가 남으면 모델은 반드시 성공한다.
5. 한국어와 영어의 일반적인 token 효율 차이를 규명했다.
6. 모델이나 provider의 장기 drift가 전혀 없다.
7. 0.4와 0.2 결과가 사전등록된 확증 실험이다.

## 13. 가장 중요한 한계와 방어 방법

### 13.1 합성 과제의 lexical 구조

요청에 `region=WEST`, `status=REVIEW`처럼 관측값과 직접 겹치는 조건이 들어 있다.
따라서 관련도 선별의 substring 일치가 실제로는 필터에 가깝게 작동한다. 특히 event에서는
정답 레코드가 항상 관련도 단독 1위였고 관련도 선별의 세 유지율 모두 30/30 성공했다.

방어 답변:

> 맞다. 그래서 관련도 선별을 범용 최첨단 방법으로 주장하지 않고, 위치만 보는 방법과
> oracle 사이의 단순하고 배포 가능한 비-oracle 기준선으로 둔다. 실제 비정형 로그에서는
> 효과가 작을 수 있으며, 이 점을 한계에 명시했다. 핵심 발견은 이 특정 선별기의 절대 성능
> 자체보다 선택 규칙이 성공당 비용을 바꾼다는 것이다.

### 13.2 단일 모델과 단일 실행

모델은 하나이고 각 방법·인스턴스는 한 번 실행했다. 동시기 B0 반복에서 4/150의 결과
불일치가 있었으므로 확률적 변동이 존재한다.

방어 답변:

> aggregate B0 성공률은 두 시기 모두 97.3%이고 비용 drift도 0.6%였지만, 개별 결과
> 2.7%가 달랐다. 이를 숨기지 않고 한계로 보고했다. 후속 국제학회 확장에서는 복수 모델과
> 인스턴스당 반복 실행이 필요하다.

### 13.3 사후 운용점 선택

관련도 선별 0.4와 0.2는 오프라인 잔존 감사를 본 뒤 선택했다.

방어 답변:

> 성공 결과는 보지 않았지만 조건 선택은 사후적이므로 탐색 실험으로 명확히 표시했다.
> 확증적 효과 크기로 과장하지 않고 곡선의 형태와 후속 가설 생성에 사용한다.

### 13.4 단순 substring

`10`이 `100`에 우연히 일치하는 문제가 생길 수 있다. 현재 방법은 이를 정교하게 해결하지
않는다.

방어 답변:

> 의도적으로 단순 lexical 기준선을 사용했다. 이 약점까지 포함한 방법이 위치 기준선보다
> 효율적이었다는 것이 관찰 결과다. 향후 typed matching, schema-aware matcher, semantic
> parser와 비교해야 한다.

## 14. 교수님이 했던 질문에 대한 현재 답

### “압축이 아니라 요약이라고 해야 하지 않나?”

생성형 요약은 아니다. 기존 JSON 레코드를 그대로 남기거나 제거하는 추출형 손실 전처리다.
‘압축’은 복원을 연상하므로 현재 원고는 상위 개념을 ‘관측 전처리/손실 축약’, 구체적 방법을
‘절단/선별’로 구분한다.

### “도구가 무슨 의미인가? 검색 엔진인가?”

도구는 레코드·일정 조회 및 상태 갱신을 수행하는 결정적 외부 API다. 검색 엔진 자체의
품질을 평가하는 논문이 아니라, 검색 결과 JSON이 다음 에이전트 행동에 들어가기 전의
전처리를 평가한다.

### “관측을 줄이는 튜닝이 실제 API에서 가능한가?”

가능하다. provider 모델 내부를 바꾸는 것이 아니라, 애플리케이션이 도구 반환값을 받은 뒤
다음 모델 API 호출의 메시지에 넣기 전에 로컬 전처리 함수를 적용한다. 현재 실험 코드가
실제로 이 구조로 동작한다.

### “성공당 비용은 무엇인가?”

실패 실행을 포함한 모든 비용을 성공 수로 나눈 값이다. 실행당 비용이 싸더라도 성공률이
낮으면 성공 하나를 얻기 위해 반복해야 하므로 비싸질 수 있다는 것을 반영한다.

### “압축 도구라는 용어가 혼란스럽다.”

현재는 ‘전처리기’, ‘균등 절단’, ‘Head-tail 절단’, ‘관련도 선별’로 구분한다. ‘압축기’는
코드 내부 구현명 또는 관련 연구를 설명할 때만 제한적으로 사용할 수 있다.

### “AI가 결정하고 AI끼리 공유하는데 연구자가 어떻게 관여하나?”

연구자는 모델의 hidden state에 개입하지 않는다. 개발자가 소유한 agent runtime이 도구
결과를 다음 모델 호출에 전달하는 과정에서 JSON을 전처리한다. 어떤 필드를 남길지는 코드로
고정된 결정적 규칙이 정한다.

## 16. 현재 논문의 논리 구조

### 초록

문제 → 비교 방법 → 데이터와 실행 수 → 핵심 수치 → 결론 순서다. 초록의 가장 중요한 숫자는
관련도 선별 0.8의 성공률 98.7%와 성공당 비용 -16.7%, 그리고 0.4/0.2의 -43.9%/-57.3%다.

### 서론

실행당 비용만 보면 싸게 실패하는 방법을 효율적으로 오해할 수 있다는 문제를 제시한다.
그 뒤 도구, 도구 관측, 전처리, 절단, 선별을 정의하고 RQ1과 RQ2를 제시한다.

### 관련 연구

프롬프트 압축, 장기 에이전트 문맥 관리, 도구 사용, 검색 문맥 요약, 비용 효율 연구와의 차이를
설명한다. 본 연구의 차이는 구조화 도구 반환값과 후속 API 행동, 성공당 비용, run 단위 잔존
감사를 함께 본다는 점이다.

### 방법

과제와 개입 지점 → 세 전처리 규칙 → 1차/후속 실험 구성 → 비용과 통계 → 잔존 감사 순서다.
심사위원이 “정답 누출 아니냐”고 물을 수 있으므로 관련도 선별이 사용하지 않는 정보가 중요하다.

### 결과

위치 절단 곡선 → 관련도 선별 곡선 → 잔존 감사 → B0 반복과 언어 token 진단 순서다.
그림 1은 실행당 비용과 성공당 비용의 방향이 다를 수 있음을 한 번에 보여준다.

### 논의와 한계

분석에서 도출된 설계 원칙을 먼저 말하고, lexical 구조의 이점, 사후 운용점, 단일 모델, 단일 실행, substring,
비정형 로그 미포함을 공개한다. 한계를 숨기는 절이 아니라 주장의 경계를 정확히 정하는 절이다.

### 결론

위치 기반 절단과 관련도 선별의 차이를 다시 요약하고 “목표 축약률보다 후속 행동에 필요한
정보의 보존 기준을 우선 정의하라”는 설계 원칙으로 끝난다.

## 17. 직접 첨삭할 때 지켜야 할 규칙

### 숫자 관련

1. ‘유지율’이 목표인지 실현인지 반드시 구분한다.
   - 그림 x축: 목표 유지율
   - 표의 유지율 열: 실현 유지율
2. 실행당 비용과 성공당 비용을 혼용하지 않는다.
3. 0.8 위치 절단은 1차 실험 값이고 나머지 곡선 점은 후속 실험 값임을 유지한다.
4. 관련도 선별 0.4/0.2는 ‘탐색적’이라는 표현을 지우지 않는다.
5. B0 drift는 ‘없다’가 아니라 ‘집계 수준에서 작았다’고 쓴다.
6. 관련도 선별 0.8은 ‘성공률을 유지했다’고 쓸 수 있지만 ‘B0보다 우수했다’고 쓰면 안 된다.
7. 균등 0.9의 -1.2%는 CI가 0을 포함하므로 절감됐다고 단정하지 않는다.

### 용어 관련

권장 표현:

- 도구 관측 전처리
- 구조화 조회 결과
- 위치 기반 절단
- 관련도 선별
- 성공당 비용
- 행동 필드 잔존 감사
- 동시기 B0
- 의미쌍 군집 bootstrap
- provider 사용량

주의할 표현:

- 압축 해제가 가능한 것처럼 들리는 ‘압축’의 무정의 사용
- 생성 요약처럼 들리는 ‘요약’의 단독 사용
- ‘검색 엔진’처럼 대상 범위를 넓히는 표현
- 관련도 선별을 ‘제안 모델’ 또는 ‘최첨단 방법’으로 부르는 표현
- ‘완벽히 예측’, ‘증명’, ‘일반화’ 같은 과한 표현

### 서사 관련

모든 문단은 가능하면 다음 연결을 유지한다.

```text
관측을 줄임 → 실행당 비용 변화 → 성공률 변화 → 성공당 비용 변화
           → 정답 필드 잔존으로 원인 설명
```

통계 기법 자체를 앞세우기보다 결과 해석을 먼저 쓰고, bootstrap과 Holm은 그 결과를 얼마나
확신할 수 있는지 설명하는 근거로 배치한다.

## 18. 발표 또는 질의응답용 짧은 설명

### 20초 버전

> 도구 사용 에이전트가 검색 API의 긴 JSON 결과를 다음 호출에 넣을 때, 단순히 앞뒤나
> 등간격으로 자르면 비용은 줄어도 실패가 늘어 성공당 비용은 줄지 않았습니다. 반면 사용자
> 요청과 관련된 레코드를 남기는 단순 선별은 성공당 비용을 16.7--57.3% 낮췄습니다.
> 핵심은 얼마나 자르느냐보다 다음 행동에 필요한 무엇을 남기느냐입니다.

### 1분 버전

> 저희는 구조화된 도구 관측을 줄이는 세 규칙을 비교했습니다. 75개 의미 과제에 한·영
> 요청을 만들고 1차와 후속 실험을 합쳐 1,950개 trajectory를 실행했습니다. 위치 기반
> 균등 절단과 head-tail은 유지율 0.6부터 0.9까지 실행당 비용을 일부 줄여도 성공 손실이
> 이를 상쇄해 성공당 비용을 안정적으로 낮추지 못했습니다. 반면 요청의 표면값과 일치하는
> 레코드를 우선 보존한 비-oracle 선별은 유지율 0.8에서 성공률 98.7%를 유지하면서 성공당
> 비용을 16.7% 낮췄고, 0.4와 0.2에서는 각각 43.9%, 57.3% 낮췄습니다. 결정적 전처리기를
> 오프라인으로 재실행한 결과 정답 필드가 삭제된 239회는 전부 실패했습니다. 따라서 배포
> 전에는 압축률보다 다음 행동에 필요한 필드와 레코드의 보존 규칙을 먼저 정해야 합니다.

### “그래서 새 알고리즘 논문인가?”에 대한 답

> 새로운 학습형 압축 알고리즘을 주장하는 논문은 아닙니다. 단순하지만 배포 가능한
> 비-oracle 선별을 추가해, 선택 규칙이 비용--성공 전이에 어떤 차이를 만드는지 실증하고
> 성공당 비용과 오프라인 잔존 감사를 포함한 평가 방법을 제시합니다.

### “결과가 너무 당연한 것 아닌가?”에 대한 답

> 필요한 정보를 지우면 실패한다는 방향은 직관적입니다. 하지만 어느 유지율에서 실행당
> 비용 감소가 성공 손실을 상쇄하는지, 위치 기반 방법과 관련도 기반 방법의 성공당 비용
> 곡선이 얼마나 다른지, 오프라인 잔존이 실제 run 결과와 어느 정도 일치하는지는 실험 전에는
> 수치로 알 수 없습니다. 본 연구는 이 직관을 1,950개 실행과 run 단위 감사로 정량화합니다.

## 19. 앞으로 ACL급으로 확장하려면

KSC 논문은 현재 이야기로 마무리할 수 있다. 국제학회 확장은 같은 논문을 길게 늘리는 것이
아니라 외적 타당성과 방법적 깊이를 추가해야 한다.

우선순위는 다음과 같다.

1. 실제 도구 로그 또는 공개 agent benchmark 추가
2. 복수 모델과 reasoning level 비교
3. 인스턴스당 반복 실행으로 확률 변동 추정
4. LLMLingua-2 또는 강한 학습형/semantic 기준선 추가
5. typed lexical matching, schema-aware 보존, semantic parser 비교
6. 자동 행동 계약 추출과 보호 필드 선택
7. 비정형 text, nested JSON, schema 변화 평가
8. 지연시간과 전처리 자체 비용까지 포함한 end-to-end 비용

현재 KSC 논문의 가장 좋은 확장 가설은 다음과 같다.

> 도구 관측 전처리의 효율은 전체 token 중요도보다, 후속 행동 계약에 필요한 필드와 레코드를
> 얼마나 정확히 식별하고 보존하는지에 의해 설명된다.

## 21. 최종적으로 이 연구는 어떻게 되었나

처음에는 “관측을 20% 줄였더니 비용은 줄었지만 성공도 줄었다”는 엄밀한 측정 사례였다.
이것만으로도 회계와 통계는 탄탄했지만, 비교점이 한 개이고 현실적인 대안이 없어 메시지가
방어적이었다.

보강 후에는 세 가지가 달라졌다.

1. 유지율 곡선을 추가해 위치 기반 절단의 실패가 한 운용점의 우연이 아님을 보였다.
2. 관련도 선별을 추가해, 같은 문제에서 실제로 성공당 비용을 줄이는 선택 규칙이 있음을
   보였다.
3. 동시기 B0와 run 단위 해시 감사를 추가해 시점 drift와 재현성 비판을 방어했다.

그래서 현재 연구의 최종 메시지는 다음과 같다.

> 도구 관측을 줄이는 것 자체는 목적이 아니다. 다음 행동에 필요한 정보를 보존하면서
> 성공 하나를 얻는 총비용을 줄여야 한다. 구조화 관측에서는 목표 token 비율을 먼저 정하기보다
> 행동에 필요한 레코드와 필드의 보존 규칙을 먼저 정의해야 한다.
